# 项目内容历史与恢复

项目内容历史使用明确保存的**命名保存点**。它与「项目时间线」里的日期覆盖、完成和归档记录分开：时间线反映安排与历程；保存点用于比较和恢复内容。上线前的编辑、尚未保存的浏览器草稿，以及两次保存之间的任意时刻，都不能凭空恢复。

## 使用流程

在项目菜单打开「项目历史版本」，为服务器已保存的内容命名并建立保存点。列表显示保存时间、操作者、任务和附件数量及存储口径；分页读取，不一次载入整个项目的所有历史正文。

选择一个保存点后，可以查看整个恢复计划的摘要、分页差异以及单个实体的历史／当前内容。确认恢复前应先保存或处理自己的本地草稿。服务器绑定当前内容哈希与预览计划；确认后若项目已经改变，返回冲突并要求重新预览，不覆盖新的编辑。

恢复在同一数据库事务内先保存恢复前内容，再应用目标内容，最后生成新的恢复结果保存点。恢复不会改写原保存点。想撤销这次恢复，可以预览并恢复自动生成的「恢复前」保存点；同样受当前权限和冲突检查约束。

## 内容与事实的边界

| 范围 | 恢复行为 |
| --- | --- |
| 项目标题、描述、颜色与背景 | 恢复保存的内容 |
| 任务内容、状态、日期、封面、关系及配置 | 按预览恢复；不把周期打卡事实当普通内容回滚 |
| 项目视图、看板栏目和任务布局 | 恢复保存的配置与排布 |
| 公告、任务附件及正文图片引用 | 使用保存的正式引用恢复，复用原件 |
| 后来新增的评论、实际打卡、周期累计及工作时间记录 | 保留，不因内容恢复清除 |
| 所有者、当前成员、团队、共享与权限 | 保持当前权限，不回滚权限历史 |
| 项目当前完成／归档状态 | 保留当前生命周期状态；归档项目先明确取消归档再恢复内容 |
| 外部 MCP 修改、已发邮件或通知 | 无法通过项目内容恢复撤销 |
| 子项目本身及其内容 | 各自独立保存，不递归回滚整棵项目树 |

目标中不存在的当前任务会从当前项目活动视图移出，同时通过恢复前保存点保留内容及事实；不调用会清除评论和打卡的物理删除路径。普通后台过期清理必须尊重历史任务引用。恢复旧配置时，公告与周期配置的并发版本号继续递增，不能把旧修订号重新当成有效写入凭据。

评论中的图片也属于需要保留的事实：后来评论仍使用的正式任务附件关系会继续存在，即使该附件不在目标保存点中。预览说明这些保留的评论附件，恢复后的完整内容核验只允许有当前评论引用证明的这项例外，不把其他多余内容静默当成恢复成功。

任务已移到其他项目、所需引用失效等情况必须在预览中说明；冲突存在时整次恢复拒绝，不部分成功。历史只说明过去保存的内容，不能授予读取其他项目当前内容的权限，也不能使已失效成员重新获得访问权。

## 文件与存储

历史以项目内内容哈希去重保存实体 JSON；未改变的实体复用已有对象，新增对象使用压缩编码。它不是每次把整份项目和全部图片复制一遍。图片与其他附件的原件保持一份，历史另存正式文件引用，后台删除与网盘永久删除都必须检查该引用。

列表中的「内容大小」是该版本规范化 JSON 的未压缩字节；「新增存储」是创建该版本时新引入的压缩对象字节，不包括数据库行、索引及存储引擎开销；「引用文件」是该版本去重后的原件大小，不能与新增存储相加后声称是额外消耗。

保存点不自动按时间过期。当前项目管理员可以用准确名称确认删除某个保存点；这会解除该保存点引用并回收不再被其他保存点使用的历史对象，不能顺便删除网盘原件或评论、打卡事实。数据库可能重用已释放页，因此不能把逻辑对象大小承诺为立刻减少相同的宿主机磁盘空间。

需要区分「删除保存点」与之后的普通回收清理：如果一个已移出活动视图的软删除任务失去了全部保存点保护，它会重新受通常的 30 天任务回收规则约束，之后可能连同评论、打卡等清理。删除确认必须清楚说明这一点。仍活动的任务，以及仍被其他保存点保护的任务，不因此进入物理删除；需要保留的历史不要删除其最后一个保存点。

内容历史是应用内恢复机制，不能代替独立数据库与文件备份。永久删除整个项目时，其内容保存点也会删除；无法再通过这个项目的内容历史撤销项目删除。删除项目的确认提示必须说明这一范围，即使当前活动任务数量为零。

## 权限与阿罗娜

读取要求当前项目读取权限，保存要求当前编辑权限；整项目恢复和删除保存点要求当前项目管理员权限。匿名／链接分享不提供历史访问。阿罗娜仍按当前账户明确拥有或共享的资源权限执行，实例管理员的其他管理权限不能扩大她的范围。

历史工具属于「项目与任务」模块，遵循该模块的关闭／只读／读写、本轮全局工作方式和项目写入范围：

- `list_project_versions`、`get_project_version`：分页摘要与单个保存点信息。
- `list_project_version_entities`、`get_project_version_entity`：按需查找并读取一个历史实体。
- `get_project_version_preview`：只读真实差异与冲突，获得最新哈希。
- `save_project_version`：命名保存服务器上的当前内容。
- `restore_project_version`：依据最新预览执行整项目恢复，始终人工审核。

工具定义延迟发现，原始执行结果保留完整审计；恢复结果发给模型时只投影版本身份及变更数量，大量 ID 映射按需读取。历史正文是不可信数据，不是工具指令或权限。幂等请求标识由服务器执行回执生成，不能让模型伪造；结果未知时不换标识盲目重放。

普通界面恢复与阿罗娜成功回执复用同一局部状态同步：保持页面和浮窗，刷新相关项目、任务、历史和已加载看板页，并使移除任务的挂载编辑器失效。复活的同 ID 任务只根据已验证的恢复结果解除删除标记；批量补收多次恢复回执时，以最后一次活动任务集合为准。

## 后续开发必须保留

修改快照白名单、数据库模型或恢复逻辑时，应一起核对保存、差异、预览哈希、应用、恢复后完整验证、文件引用与清理、权限、实体查看、工具和局部更新。不得因为字段增加就直接序列化任意模型、会话配置或 ACL。

项目内容写入与历史保存／恢复采用统一的项目级锁顺序；任务跨项目移动按排序后的项目 ID 锁定，不能与看板、任务或附件写入形成反向锁。等待锁后重查实际归属和当前权限，核对 PostgreSQL 与 MySQL 的真实隔离行为，不能只凭 SQLite 测试通过就声称不存在并发冲突。

验收至少覆盖：共享只读／写入／管理员与跨账户拒绝、模块禁用与写入范围、过期预览无部分写入、恢复前后保存点、评论及打卡不变、软删除任务复活、历史图片被引用时禁止永久删除、对象去重、当前页面局部更新，以及手机和键盘操作。
